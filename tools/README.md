# EO development content importer

`import_eo.py` converts one map and its referenced graphics to the Godot content contract. It does not launch legacy executables, extract executables, start a server, or fetch source archives automatically. ZIP members are size limited and read in memory; output filenames are generated by the importer.

Requires Python 3.10+ and Pillow (`python3 -m pip install Pillow`). Run from the repository root after obtaining source archives you have permission to use:

```sh
python3 tools/import_eo.py \
  --sample-data /path/to/sample-data.zip \
  --client-zip /path/to/EOzipped028.zip
python3 tools/test_import_eo.py
```

To import elsewhere use `--output /absolute/path/to/client/content`. The `--map` argument selects a numbered map, default 5 (Aeven). For tests, `EO_DATA_DIR` can override the source archive directory. Real-data integration checks skip when the archives are unavailable. Reference archives and generated assets are not included in the public repository. Keep local downloads in the ignored `reference/` directory.

The default export is the complete 87×87 Aeven map, not a synthetic approximation. Spawn `(40,40)` has a clear seven-by-seven neighborhood. The importer preserves 26 map NPC spawn records, chest and warp records, encoded map text, all nine layers, and tile specifications. It exports only the map's referenced graphic IDs, selected item samples, and character frames. NPC records and warps are reference data; their presence does not imply runtime AI, transitions, quests, or network support.

`manifest.json` records source archive hashes, exact source URLs, graphics paths/dimensions, layer mapping, character frames, sound effects, and limitations. Character sprites are composed from classic male skin, hair, armor, and boots using the source renderer's frame selection and offsets. The prototype precomposes eight equipment combinations and switches among them at runtime; arbitrary equipment compositing is future work. `manifest.characters.hero_variants` keys are `a0_b0_w0` through `a1_b1_w1`, where the bits select armor, boots, and weapon. Every combination includes the complete four-direction idle, walking, and attack animation sets. `hero` aliases `a1_b1_w0`; `hero_equipped` aliases `a1_b1_w1`. `source_resources` records source EGF members and graphic IDs for each variation. The training creature uses green slime graphic 3, with its actual individual standing, walking, and attack resources. Frame dictionaries are keyed `south`, `east`, `north`, `west`. Each frame has `path`, `region:[x,y,w,h]`, and `offset:[dx,dy]` relative to a bottom-center entity anchor. Hero frames include eight transparent pixels below the feet, represented by offset `[0,8]`.

`manifest.sounds` includes melee attack, inventory pickup, and punch effects from `sfx016.wav`, `sfx021.wav`, and `sfx011.wav`. The reference melee file reports an incorrect RIFF length and has extra bytes after its declared PCM data. The importer writes canonical WAV files from the declared PCM frames with exact lengths; the manifest preserves original member names/hashes and repair metadata. No MIDI conversion is included.

`manifest.starter_equipment` is parsed from the original client’s `pub/dat001.eif`, rather than guessing which icons match the character: armor is Soldier Plate (item143, male armor graphic1, icon312), boots are Blue Boots (item80, boot graphic1, icon176), and weapon is Dagger (item21, weapon graphic4, icon76). These are local prototype appearance definitions; the separately supplied server PUB data may use different identifiers. Every equipment entry includes its source member and ground/inventory graphic keys.

`manifest.paperdoll` includes the original male paperdoll background and silhouette panel, extracted from GFX2 graphic49, plus the fifteen original equipment slot rectangles. Crop rectangles and the source member are recorded. The original panel is 380×290; the silhouette crop is 200×266. Both retain opaque UI colors rather than using sprite color-key transparency.

Building alignment follows the base renderer’s per-layer offsets in addition to each specialized renderer. In particular right walls have a +32px horizontal offset relative to down walls; omitting that base offset splits house corners. With this client’s tile-center basis, down walls draw at `(-32,15-height)`, right walls at `(0,15-height)`, objects/overlays at `(-width/2-2,14-height)`, roofs at `(-32,-80)`, top tiles at `(-32,-48)`, and shadows at `(-56,-28)` with alpha0.2. `manifest.reference_layer_offsets` documents the exact mapping. Aeven’s visible building tops are largely object sprites; this map contains no entries in the dedicated roof layer.

The current twelve tests cover base-253 number boundaries, an independently captured encoded Aeven-name fixture, truncated input, archive traversal/size rejection, all 289 real map files, known Aeven counts, walkable spawn, PE resource offsets, black color-key transparency, every exported map graphic reference, character frame dimensions, repair of the malformed WAV header, actual classic item definitions, and eight pixel-distinct equipment combinations.

Reference implementation: [EndlessClient](https://github.com/ethanmoffat/EndlessClient), especially `EOLib.IO/Services/Serializers/MapFileSerializer.cs`, `MapPropertiesSerializer.cs`, `MapStringEncoderService.cs`, `Rendering/Sprites/CharacterSpriteCalculator.cs`, `NPCSpriteSheet.cs`, character property renderers, map entity renderers, and `Audio/SoundEffectID.cs`.
